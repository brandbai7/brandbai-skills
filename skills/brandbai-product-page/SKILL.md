# BrandBAI 商品页诊断优化

先建立当前细分类目的用户购买决策链，再还原主图、交易区和详情页的内容信息链；逐项判断页面有没有承接、出现位置是否合适、证据是否接得上、信息是否重复或过载，最后用“认对、看懂、相信、选对、放心买”做跨品类验收，并优先收敛为一至三项整体改版项目，确有必要时最多五项。页面长度不是质量指标，购买决策是否闭合才是。

## 先确认许可与对象

只在 [PolyForm Noncommercial License 1.0.0](references/license.md) 允许的非商业范围内运行。企业内部使用、客户交付、收费课程配套或其他预期商业用途，须先通过 `brandlaobai@163.com` 取得 BrandBAI 书面商业授权或课程内附的明确授权。

一次运行只处理一个品牌、一个商品、一个页面主讲 SKU／套组和一个页面版本。先从主图与详情页识别页面实际上围绕哪个 SKU 组织主要内容，再到交易区可见选项中核对该 SKU 是否仍可成交。商品页分析不评价采集工具的选中过程，也不把采集过程写入品牌报告。

只有在页面主讲 SKU 无法识别、页面由多个 SKU 混合且没有明确主讲对象，或页面主讲 SKU 不在可见成交选项中时，才停止正式改版并输出核实清单。用户明确指定并确认某个可成交 SKU 时，也可把它作为分析对象，但仍要检查页面材料是否真正适用于它。

本 Skill 只处理静态商品页。下载页面、建立完整商品价值底座、生成短视频／达人／直播内容、制作最终视觉稿和发布页面都属于其他任务，不自动串联。

## 选择两种模式

默认根据输入自动选择：

### `diagnose_existing`

只有当前商品页也可以运行。允许：

- 盘点页面当前在说什么、展示什么；
- 识别页面目前试图建立的核心购买理由，并明确它只是“页面当前主张”；
- 检查一核、五决策、SKU／套组、主图—交易区—详情一致性；
- 给出保留、删除、补充、前移、重新组织、人工核实中的零至五项动作；
- 标出哪些建议可直接做，哪些必须补资料后再做。

不得从页面宣传语反推客观商品事实，不得新造卖点、功效、数字、竞品优势或用户共识。

### `enhance_with_evidence`

除页面外，用户又提供了包装、参数、配方／工艺、检测／专利／认证、用户研究、评论样本、客服／退货问题、目标人群、主推 SKU、渠道任务或竞品页面等资料时使用。

先逐份登记资料能证明什么、适用于哪个 SKU、不能证明什么，再把可用内容编译为更完整的主图顺序、交易区信息和详情页模块。竞品页面只能支持结构与表达比较，不能证明本商品事实。评论只能作为顾虑、语言和场景信号，不能单独裁定功效。

若用户已经提供有效的 `brandbai-product-value` 或 `brandbai-value-expression` 交付，可以直接继承其事实、价值、VIS 与限制；它们是可选增强输入，不是启动本 Skill 的强制前置。

## 准备最低输入

最低需要：

1. 商品名；
2. 页面主讲 SKU／套组及交易区当前可见成交选项；
3. 至少一部分可视觉读取的主图、交易区或详情页材料；
4. 页面快照或观察时间；不知道时写 `unknown`。

模型必须逐张打开图片或逐页打开 PDF，确认真实顺序、页面位置和可读范围。不能只看文件名、缩略图、OCR 汇总或旧报告。未提供的页面范围写“未提供／无法确认”，不能写成“页面没有”。

补充资料是可选项，不要为了启动诊断向用户索要经营后台、GMV、ROI 或完整商品价值工程。资料减少时结论变弱，但诊断仍可完成。

当输入来自 BrandBAI 天猫商品下载包时，优先读取 `SKU主图映射` 与全部 SKU 读取状态：

- `complete_all_visible_skus`：按页面主讲 SKU／用户确认 SKU 选择对应主图库，再做主图顺序与实际到手判断；
- `complete_single_sku`：页面只有一个可成交 SKU，可直接继续；
- `partial_all_visible_skus`：已读取部分 SKU，只有目标 SKU 有明确映射时才诊断其主图；其余 SKU 保持未知；
- `current_selection_only` 或没有 SKU—主图库映射：仍可诊断共用详情页与页面整体表达，但不得把当前选中 SKU 的主图、价格、赠品和实际到手推广为页面全部 SKU，也不得正式给出其他 SKU 的主图改版结论。

以上状态只用于选择正确页面材料，不写入品牌报告，也不评价下载过程。

## 初始化交付

先 Dry Run：

```powershell
python scripts/init_product_page_delivery.py `
  --out "<新的输出目录>" `
  --page-sources "<主图、交易区截图和详情页目录>" `
  --brand "<品牌>" `
  --product "<商品>" `
  --sku "<当前SKU或unknown>" `
  --analysis-mode diagnose_existing `
  --scope combined `
  --delivery-mode professional `
  --page-snapshot-time "<时间，未知写unknown>" `
  --dry-run
```

增强模式可增加：

```powershell
  --analysis-mode enhance_with_evidence `
  --supporting-sources "<补充资料目录>" `
  --product-value "<可选：商品价值交付目录>" `
  --value-expression "<可选：卖点呈现交付目录>"
```

确认目标后去掉 `--dry-run`。输出目录非空时拒绝覆盖。

## 完成诊断与优化

按顺序完成：

1. 锁定商品、页面版本、范围、真实顺序与可读性；先识别页面主讲 SKU／套组，再核对它是否存在于交易区可见选项；存在多 SKU 时，必须把分析对象与对应主图库唯一映射后再评价主图；
2. 逐项登记页面原话、可见画面、动态权益和适用对象；
3. 先建立细分类目用户购买决策链：说明用户依次需要确认什么、哪些是必答、判断依据来自哪里，以及当前成熟度；只有页面材料时必须标为工作假设；
4. 再按真实顺序还原页面内容信息链，并让每个内容节点关联至少一个细分类目购买任务；`dominant_route` 只能描述页面现在实际怎样讲，不得写入优化后建议路线；
5. 对每个细分类目任务分别判断有没有承接、位置是否合适、证据是否接上、信息是否重复或过载，形成完整双链匹配账本；
6. 先还原当前页面的整体策略、成交逻辑和页面当前核心购买理由；
7. 先总结现有页面中建议继续保留的内容，再从双链断点收敛为最多三个整体根因；根因必须说明页面依据、购买影响和涉及的购买判断，不评价品牌或页面“做对／做错”；
8. 给出整体重构策略：本轮目标、新版购买逻辑、连续叙事路线，以及主图、交易区、详情页和决策收口的分工；
9. 依次判断认对、看懂、相信、选对、放心买，状态只用“已讲清、部分讲清、未讲清、资料不足”；五决策只做跨品类验收，不替代细分类目任务；
10. 按页面位置选择不同执行粒度：主图逐张安排主要任务，交易区先判断是否需要调整，详情页按连续内容章节重构；旧详情图只作为素材来源，不得在品牌报告中逐张生成优化建议；
11. 为交易区建立独立 `transaction_panel_plan`：交易区每次都要检查，但不是每次都要改。只有规格难以区分、主图／选项／实际到手不一致、不同商品混在同一选择区，或动态优惠明显干扰用户选对时，才把交易区纳入改版。需要调整时，天猫／淘宝默认只允许一个主要规格选择区；容量、商品类型、套组、稳定到手和简短选择理由在同一组选项中表达，用户阅读顺序不得被写成多个平台选择器。已经能够支持用户选对和确认到手时，状态写为 `preserve_only`，不生成选择区改版卡。只有平台当前页面或品牌后台已经证明可以实现的结构才进入正式建议；无法确认能实现的交互不写入改版方案；
12. 建立 `detail_page_assessment`：结合细分类目购买任务链与认对、看懂、相信、选对、放心买五个判断，分别说明现有详情页已有优势和还可提升之处；不得为了显得专业而制造优缺点；
13. 为详情页建立独立 `detail_page_plan`：先写整页任务与新版讲述路线，再形成内容地图；每个内容章节必须写明用户问题、页面答案、必含内容、可调用现有素材、呈现方向、待补资料和完成标准；
14. 把所有已读详情页内容节点完整登记到新版安排表，逐项决定继续使用、集中到一个章节、分别放入不同章节、提前说明、放到后面、本轮不使用或确认后再安排，并指向新版内容章节；一个章节可做成连续多个视觉画面，多个旧内容也可集中到一个章节；
15. 增强模式把补充资料登记为事实、页面主张、用户信号、动态快照或待核实主张，并继承适用范围；
16. 按“细分类目任务断点、整体根因影响、证据确定性、本轮可执行性”排序，只留下零至五个改版项目；每个非保留项目必须绑定至少一个未解决的细分类目任务和至少一个整体根因；
17. 每项标为“可直接优化／补充资料后优化／待上线验证／不建议使用”；
18. 先输出品牌可直接阅读的“最影响下单的问题”、详情页已有优势与提升空间、改版后建议路线和改版项目，再把五个买前问题压缩为需要时再看的复核表；随后输出主图逐张任务、交易区可实施方案、详情页内容地图、现有内容安排、资料缺口、禁用表达和最小验证问题。普通正文最多展示三个关键问题，每项只写页面现状与购买影响，承接／位置／证据／重复等完整审计状态只留在 `data/`。

品牌可见报告必须使用业务语言：把可用补充资料写成“品牌内部商品资料／可直接使用的卖点资料／页面公开信息”，把下一步写成“补充资料、人工确认或上线后观察”。`商品价值上游`、`卖点呈现上游`、`返回上游`、`商品价值底座` 等内部流程词只允许留在 `data/`，不得出现在两份普通版报告中；普通报告中的 SKU、动态权益分别写成“商品选项”“当前优惠”。

品牌可见报告不得使用脱离明确排期就会过期的“明天、下周、首周、本月”等时间词，统一改为“建议先做／优先启动／完成后”。每个改版项目只展示：要解决什么、具体怎么改、主要落点、需要准备、完成标准、保留内容；建议标签、内部状态、调用依据和完整验证字段保留在 `data/`，不要把动作账本逐字段摊开。

每个购买判断不能只写“部分讲清”。必须分别写清：页面已经讲清什么、还没讲清什么、这会怎样阻碍购买、应当怎样补。优先动作只针对“还没讲清”的部分；已经讲清且没有关键缺口的判断只保留，不进入优化优先级。

诊断使用“够用即可”而不是“每处都要最严”：一个信息只要在消费者做决定前的合适位置讲清，就不要求在首图、交易区和详情页重复出现。首图不必塞满总克重、全部参数和所有边界；交易区或详情页已经清楚承接时，不把未重复写入首图判为缺口。页面公开主张可以先做层级、顺序和理解优化；只有要把它升级成已确认事实、精确证明或高风险承诺时，才要求补原始证据。

检测、认证、专利或报告与当前 SKU 存在差异时，先判断“差异是否影响正在证明的结论”，不能见到克重、包装或罐数不同就自动判无效：

- 包装总克重、罐数、包装版式不同，但产品身份、配方／原料、生产主体与检测项目一致时，通常只收窄为商品级或系列级参考，不自动阻断；
- 如果检测的是净含量、单包装量等与差异字段直接相关的项目，克重不同会影响结论；
- 配方、原料、产品形态、型号、适用对象、生产主体或被检测项目发生实质变化时，才按证据错位处理；
- 无法确认关联性时标为“适用范围待确认”，不写成无效，也不写成当前 SKU 专属证明。

五决策不是五张图，页面模块也不必凑齐固定数量。页面短但决策已闭合，不为凑长度补内容；页面长但关键任务未闭合，也不能因信息多判定为好。

详情页内容章节也不是详情图张数。品牌报告只呈现新版整页逻辑、少数整体项目、内容地图和素材迁移；不得把旧详情图按张序重新列成“每张优化一点”的清单。只有主图仍按张序输出，因为主图位置有限且每张承担明确的前台任务。

## 生成与校验

```powershell
python scripts/build_product_page_report.py --delivery "<输出目录>" --dry-run
python scripts/build_product_page_report.py --delivery "<输出目录>"
python scripts/validate_product_page_delivery.py --delivery "<输出目录>"
```

普通入口固定为：

```text
01_商品页诊断与优化建议.md（正文标题为“商品页诊断与优化方案”）
02_主图交易区详情页优化页纲.md（正文标题为“商品页改版执行方案”）
```

专业模式固定交付两份正式文档：`01` 面向品牌负责人，含整体诊断、改版优先级、资料缺口与证明边界；`02` 面向电商、文案和设计团队，含主图、必要时的交易区与详情页执行方案。只有医疗器械、婴幼儿食品等高风险商品在用户明确需要时，才从 `data/` 另行整理证据附件，不把第三份 Markdown 作为默认交付。

宿主具备可靠电子表格能力时，可按 `02` 的相同字段另导出 `.xlsx`；Markdown 是跨模型必交底稿，Excel 不是完成门槛。内部来源、模块、判断、动作、验证和缺口保留在 `data/`。只有校验退出码为 `0` 才能正式交付。

## 严格边界

- 页面出现不等于事实成立，公开主张不等于独立验证；
- 高销样本只支持方法覆盖，不证明页面结构导致销量；
- 静态诊断不等于改版已经提升点击、转化、GMV、ROI 或销量；
- 限时价格、赠品、库存、物流和权益只能作为带时间的动态快照；
- 其他 SKU、色号、口味、尺码、段位、月龄、包装和套组证据不能自动迁移；
- 商品页报告不评价或披露下载、采集过程；只使用当前页面可读内容和可核验补充资料；
- 页面承诺、页面主讲 SKU 与实际到手冲突时，先核实，不继续美化；
- 最终视觉稿、完整成品文案、合规审核和发布仍需对应负责人确认。
